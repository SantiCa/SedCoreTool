# M2.1.5 Multiproxy: the depth-age relation is built once per core

Card M2.1.5 of [the roadmap](../roadmap.md), found by [M2.1.4](M2.1.4.md). Raw data: [M2.1.5-windows.json](M2.1.5-windows.json) (3 repetitions per size; same tool and
fixture as M2.1.4: `tools/measure_large_tables.mjs --parts figures --rows 20000,100000 --reps 3`). Same computer: Windows 11, Ryzen 7 7700X, Chrome 157 headless.

## What changed

`app/js/geo.js`: `coreConverter(core, from, to)` builds the ages, the depth-age pairs and their order once and returns a function that converts one value;
`coreConvert` is a wrapper with the same signature and result. `buildSamples` prepares the two directions once per core instead of calling `coreConvert` twice for every
sample, and `intervalsOnAxis` prepares one conversion per source axis instead of two per interval. The interpolation (`interpAge`) and its edge behaviour are untouched,
and nothing is cached beyond the call, so edits to a core's arrays are always seen. The unused helper `lerp` was removed.

Tests: `tests/app/geo-convert.test.mjs` (7 tests) were written first and passed on the old code; they keep a copy of the old implementation and compare it with the new one
with `Object.is` on 300 random cores (nulls, unsorted rows, repeated values, age-only cores, clamp on and off, both directions), and check every sample of `buildSamples`.
`node --test` 368 passed; typecheck passed.

| Multiproxy log, first opening | 7,744 ms -> **240 ms** (234-255) | 195,269 ms -> **2,450 ms** (2,403-2,594) |

(cross-plot redraw 135-139 ms at 50,000 points) are close to M2.1.4 (156 ms there, a different run).

## Verdict against the card

The goal was a first opening of **at most 2 s** at 100,000 rows. **It is not met: 2.4-2.6 s**, 80 times faster than before. The profile of the cold opening (a separate run, 2,460 ms
with the profiler) puts the rest in two other places of the same function, not in the conversion:

- `buildSamples`, `geo.js:188`: 1.15 s. For every sample and every interval category the code scans all intervals of the core with `ivs.some(...)`, so the cost is
  samples x categories x intervals (about 50,000 samples and 1,000 intervals here). `createIntervalLookup`, already in the same file for half-open boundaries, answers this without a scan.
- `buildSamples` itself (0.58 s of its own work, the grid and the resampling) and the labelling of samples by interval (`geo.js:319`, `intervals.find` per sample, about 0.25 s).

The fixture has 1,000 intervals per core in two layers (100-row bands); the scan scales with that number, so a core with fewer intervals scans proportionally less. Not measured with other counts.

## Not measured

macOS, Linux, a real display; projects with other numbers of intervals; the cross-plot and the Data table (unchanged).
