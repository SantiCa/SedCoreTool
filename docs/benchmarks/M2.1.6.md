# M2.1.6 Multiproxy: interval membership with a lookup

Card M2.1.6 of [the roadmap](../roadmap.md), proposed by [M2.1.5](M2.1.5.md) and authorised by the maintainer on 16 November 2026. Raw data:
[M2.1.6-windows.json](M2.1.6-windows.json) (3 repetitions per size; `tools/measure_large_tables.mjs --parts figures --rows 20000,100000 --reps 3`). Same computer and fixture as M2.1.4 and
M2.1.5: Windows 11, Ryzen 7 7700X, Chrome 157 headless; the fixture has 1,000 intervals per core in two layers.

## What changed

`app/js/geo.js`, two places that scanned every interval for every sample:

- `buildSamples`: the 0/1 column of each layer category ("some interval of this layer and category contains the sample") now uses one `createIntervalLookup` per
  (layer, category) group instead of `ivs.some(...)` over all intervals.
- `labelSamples`: one lookup per core instead of `iv.find(...)` over all intervals; intervals keep their original order inside each core, so the first match still wins.

`createIntervalLookup` (already in the file, half-open boundaries) falls back to the linear predicate whenever intervals overlap or have non-finite or reversed ends,
so the results are the same in those cases too. Comparison keys use `Map`, which treats `NaN` as equal to itself while `===` does not; ids and categories are strings, so this
cannot differ in practice.

Tests: `tests/app/geo-intervals.test.mjs` (5 tests) were written first and passed on the old code. They keep copies of both old implementations and compare them with the new code on random
projects (two cores, two layers, 63 intervals including auto and empty ones, shared boundaries and an exact duplicate, both axes, each layer filter), and on a hand-built core whose intervals
have reversed, open-ended, string-valued and `NaN` ends (for the category columns of `buildSamples`). Two more tests cover an unknown core and no intervals in `labelSamples`, and check that the comparison is not trivial (both outcomes occur).
`node --test` 373 passed; typecheck passed; `tests/e2e/smoke.mjs` result in the card.

## Results (3 repetitions; the three values in brackets)

| Case | 20,000 rows: M2.1.5 -> now | 100,000 rows: M2.1.5 -> now | At the start (M2.1.4, 100,000) |
|---|---|---|---|
| Multiproxy log, first opening | 240 ms -> **159 ms** (155-169) | 2,450 ms -> **576 ms** (540-617) | 195,269 ms |
| Multiproxy log, redraw after a setting | 153 ms -> 151 ms | 512 ms -> 509 ms (498-516) | 613 ms |

The drawn log is identical (1,112 SVG elements and 2,080,918 characters at 100,000 rows, as in M2.1.4 and M2.1.5).

## Verdict against the card

The target of M2.1.5 was a first opening of at most 2 s at 100,000 rows: **met (0.54-0.62 s)**, 340 times faster than the 195 s found by M2.1.4. The redraw after a setting
(about 0.5 s at 100,000 rows) did not change and was not part of the target; its time is not examined here.

## Not measured

macOS, Linux, a real display; other numbers of intervals; a profile of the remaining 0.58 s of the first opening; the multiproxy classifier training and prediction on 50,000 samples
(other code paths that use `labelSamples`, covered by the equality tests but not timed).
