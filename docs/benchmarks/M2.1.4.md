# M2.1.4 Tables and figures with 20,000 and 100,000 rows

Card M2.1.4 of [the roadmap](../roadmap.md). It measures only; the program was not changed. Target: the last row of the interactive targets of
[contract §7](../roadmap-engine-contract.md#7-predeclared-verification-and-performance-gates) (frame interval p95 <= 33 ms).
Raw data: [M2.1.4-windows.json](M2.1.4-windows.json). Tool: `tools/measure_large_tables.mjs`.

## Method and environment

Windows 11 (10.0.26300), AMD Ryzen 7 7700X (16 logical CPUs), 31.1 GiB RAM, Chrome 157.0.8103.51 headless at 1,440 x 900, Node 22.23.4, puppeteer-core 23.
The real application is served by a local static server and driven through its own controls. Fixture: the deterministic M2.1 project
(`tools/data_table_fixture.mjs`: two cores, six numeric columns, every 37th value missing), 20,000 and 100,000 rows in total, so 10,000 / 50,000 points per core
and 20,000 / 100,000 for both. Time is click -> forced layout -> two animation frames (the boundary of M2.1.2). Frame gaps are `requestAnimationFrame` intervals.
Each case runs in a fresh browser: **3 repetitions** for the table and for the 20,000-row figures, **1 repetition** for the 100,000-row figures (the
tool was changed once during the card, see "Not measured"), with a CPU profile in the last repetition. Scrolling: 5 s of programmatic `scrollTop` steps at
about 52,000-73,000 px/s over the whole reachable travel.

## Data table (3 repetitions, medians; scroll p95 as the range of the three)

| Rows | Rendering | Open | 10 x "Show more" | DOM rows / elements | Scroll frame gap median / p95 / max | Verdict (p95 <= 33 ms) |
|---|---|---|---|---|---|---|
| 20,000 | native | 45 ms | 6,049 ms | 10,400 / 135,237 | 79 / 96-100 / 100-108 ms (62-66 frames in 5 s) | **fails** |
| 20,000 | visible rows only | 19 ms | 111 ms | 37 / 537 | 4.2 / 8.3-8.4 / 13 ms | **passes** |
| 100,000 | native | 79 ms | 5,571 ms | 10,400 / 135,237 | 75-79 / 92-100 / 96-138 ms | **fails** |
| 100,000 | visible rows only | 49 ms | 122 ms | 37 / 537 | 4.2 / 8.4 / 13-17 ms | **passes** |

- **A table of 100,000 rows is never fully scrollable today.** The table shows 400 rows and 1,000 more per "Show more", so ten expansions give **10,400** rows
  at most for both sizes; the numbers above are the largest reachable table. Reaching row 100,000 is not possible in either rendering.
- Native: about 13 frames per second while scrolling (62-67 frames in 5 s), and the profile puts the time in `renderDataTable` (2.5 s of a 20 s profile) and in the
  browser's own layout and paint of 135,000 elements.
- Visible rows only (flag M2.1.3, off by default) is within the target at both sizes, with 37 rows in the DOM; this agrees with [M2.1.3](M2.1.3.md).

## Figures (medians of 3 at 20,000 rows; 1 repetition at 100,000 rows)

| Case | 20,000 rows | 100,000 rows | Target | Verdict |
|---|---|---|---|---|
| Open the plot view | 21 ms | 74 ms | gap <= 33 ms | 20,000 passes; 100,000 **fails** |
| Depth plot (lines), one core: 10,000 / 50,000 points | 20 ms, 34 SVG elements | 25 ms, 34 elements (572 KB of SVG) | gap <= 33 ms | passes |
| Cross-plot (scatter), one core: 10,000 / 50,000 points, redraw after a setting | 36 ms, 9,770 elements | **156 ms**, 48,689 elements (3.0 MB) | gap <= 33 ms | 20,000 **fails** (marginally); 50,000 **fails** |
| Cross-plot, add the second core: 20,000 / 100,000 points | 64 ms, 19,492 elements | **315 ms**, 97,330 elements (6.6 MB) | gap <= 33 ms | **fails** |
| Cross-plot, two cores, redraw after a setting | 60 ms | **329 ms** | gap <= 33 ms | **fails** |
| Multiproxy log, **first opening** of a core | **7,744 ms** (7,720-7,764) | **195,269 ms (3.3 minutes)**, 195,114 ms in a second run | gap <= 33 ms | **fails by orders of magnitude** |
| Multiproxy log, redraw after a setting (cached) | 147 ms, 331 SVG elements | 613 ms, 1,131 elements (2.7 MB) | gap <= 33 ms | **fails** |
| Mouse moves over a figure (60 moves; no per-point handler exists) | frame p95 4.3-8.3 ms (max 20.8 ms) | frame p95 4.3-12.5 ms (max 41.7 ms) | p95 <= 33 ms | passes (but see below) |

- The scatter plot writes **one `<circle>` per point** as a string and replaces the whole SVG on every change (`drawDataPlot`): the redraw time is proportional to the
  points (about 3 ms per 1,000 points) and blocks the page for that long. At 100,000 points the profile shows `drawDataPlot` (assigning the 6.6 MB string and the browser's
  parse) and `drawSeries` as the slowest steps; the browser's own layout is the rest.
- The depth plot draws lines as one `<path>` per series, so its cost is the length of the path string, not the number of points; it is not a problem at 50,000 points.
- **Multiproxy, first opening: 195 s at 100,000 rows.** The profile of that opening (`profile_multiproxy_first_open` in the JSON) attributes about 129 s to
  `coreConvert` (`app/js/geo.js:103`) itself and about 180 s with the anonymous functions inside it, plus 13 s of garbage collection. `coreConvert` rebuilds and sorts
  all depth-age pairs of the core every time it is called, and `buildSamples` calls it for every sample of the grid (`geo.js:170-171`), so the cost grows with the square of the
  rows. 7.7 s at 20,000 rows and 195 s at 100,000 rows are a factor 25 for a factor 5 in rows. The later redraws do not repeat it (cached).
- There is no hover or selection of a single point in these figures (the SVG has no per-point handlers), so "response to hovering and selecting a point" cannot be measured as
  such; the table row measures what the browser spends while the mouse moves over the figure. A headless Chrome renders frames every 4.2 ms (without a screen's refresh
  limit), so a p95 of 4.3 ms says that nothing blocks, not that a monitor shows 240 frames per second.

## Inputs for the design session (not decisions)

1. The visible-rows table is already within the target at the sizes measured (decision 1 of the roadmap's waiting list); what still limits large tables is the
   400 + 1,000-row expansion limit, which is a product limit, not a rendering one.
2. The multiproxy first opening is a defect of complexity in one function, independent of the tile store and of the engine; it affects projects of about 20,000 rows and more
   and would also matter for the Python migration of that code. Building the depth-age pairs once per core would remove the square.
3. A scatter of 50,000 points as individual SVG elements cannot meet 33 ms in this program; a canvas drawing, or binned/density drawing, or limiting the drawn points,
   are the options to compare. The depth plot is not affected.

## Not measured

- macOS, Linux, a real display (headless only), CPU profiles of all repetitions (the last of each case only).
- The 100,000-row figures ran once (the time per step exceeded the tool's first protocol limit of 180 s, which was raised; the cold opening of the multiproxy log
  took 195 s in both runs that completed, so the single value is not a lone outlier). The row "Cross-plot, one core, 50,000 points, redraw" is therefore not a median.
- Memory of the page while drawing the figures (the card did not ask for it), saving or exporting a figure, and zoomed or panned figures (the figures have no zoom).
