# M8.4.20 - Interval sums without a per-interval loop, and rule D11 measured again (Windows, development evidence)

Raw data: [M8.4.20-interval-table-windows.json](M8.4.20-interval-table-windows.json) (`tools/measure_interval_table.py`) and
[M8.4.20-round-trip-windows.json](M8.4.20-round-trip-windows.json) (`tools/measure_engine_analysis.mjs --only scenarios --pairs 20 --synthetic`).
Same computer and stand-in project as [M8.4.12](M8.4.12-round-trip-summary.md) (the package has the same SHA-256, `b5835773...`). The raw JSON records the
commit `f4ec92a` because the measured changes were not committed when the tools ran; they are in the commit that adds this file.

## What changed (no result changes)

- `kernels/binning.sum_by_interval`: integer and boolean values (the row counts) are summed in one pass (`np.add.reduceat` when the intervals are
  consecutive, one cumulative sum otherwise) instead of one NumPy call per interval. Float values and negative edges keep the original loop.
- `kernels/binning.bin_edges`: all boundaries computed at once with the same arithmetic as `bin_edge` (`floor(j * bin_px + 0.5)`) for `bin_px >= 1`; the loop stays below 1.
- `methods/section_intervals.run`: the bioturbation and class sums were computed twice from the same data; now once.
- Tests (`tests/test_kernels.py`): exact equality against the previous implementations kept in the test, for nine dtypes, scalar and trailing axes, empty,
  reversed, overlapping, out-of-range and negative edges, integer overflow, and `bin_edges` for 75 interval sizes including fractional and just-below/above integers.
  `pytest` 724 passed / 9 skipped; the legacy regression and the engine's fixture check with NumPy 2.2.6 pass.

## Results

| | Before (M8.4.12) | Now |
|---|---|---|
| Remembered counts -> table, 349,526 rows (17,476 intervals), median / p95 | 237.7 / 671.1 ms | **34.8 / 38.9 ms** (20 calls; NumPy 1.26.4 in-process) |
| One-tile edit, engine on, edit + undo + redo, median / p95 / max | 71.9 / 793.8 / 793.8 ms (18 samples) | **71.0 / 84.7 / 86.4 ms (60 samples)** |

The 794 ms stall of M8.4.12 did not recur in 60 samples (1 in 78 over both runs). The remaining 35 ms are the work itself: 5.6 million
row counts are read once per call.

## Rule D11 (contract §7), applied again

p95(edit) + median(table) = 84.7 + 34.8 = **119.5 ms > 100 ms. The outcome is still D**, now by 19.5 ms and on numbers that no longer contain an
implementation artefact or a one-off stall. The rule was not changed.

## Decision recorded

Executed on the maintainer's delegation of 16 November 2026 ("ejecuta lo que harías tú"): **D is accepted** for the interactive interval table of tiled
sections (it stays in JavaScript, with the Python method as reference and the parity tests), narrowly, as ARCHITECTURE §3.4 rule 8 already provides.
The maintainer can overrule it. If it is overruled in favour of A, the 19.5 ms would have to come from the chain (bridge calls, the page's full hash and
redraw, M8.4.5) and not from the kernel. The vectorised kernel also speeds up the Python API and the command line.

Not measured: macOS and Linux, a clean machine, saturated CPU, the NumPy 2.2.6 of the engine for the in-process timing (the engine's own run is in the round-trip file).
