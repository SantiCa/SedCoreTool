# M8.4.12 - Round trip of a one-tile edit, and rule D11 (Windows, development evidence)

Raw data: [M8.4.12-round-trip-windows.json](M8.4.12-round-trip-windows.json) (the scenarios tool, see below) and
[M8.4.12-interval-table-windows.json](M8.4.12-interval-table-windows.json) (`tools/measure_interval_table.py`). Same computer as M8.4.1 (Windows 11, Ryzen 7 7700X,
31 GiB, Electron 45.2.2, bundled Python 3.12.16 for the engine; Python 3.12.4 and NumPy 1.26.4 for the in-process table timing), run from source.

## What was measured

1. **The chain of a one-tile edit.** Stand-in project: eight sections of 512 x 512 pixels (one tile each; `make_synthetic(path, height=512, width=512)`, seed 138501,
   547,036 bytes, SHA-256 `b583577316b010d7b6f92ce28044ccd75b488403c9eb27b2a208a361c8228b62`; the default 960 x 6400 package is byte-identical to before, shown by hash and by a test).
   `node tools/measure_engine_analysis.mjs --only scenarios --pairs 6 --synthetic <package>`: scenario (b), the deletion of one trace, its undo and its redo, through the
   interface, the page, the main process, the coordinator and the worker, 18 samples with the engine on. The public example is measured by the same run and is not used here.
2. **Row counts -> table.** `py -3.12 tools/measure_interval_table.py`: one section of **349,526 rows** (the height of the 8 GiB fixture of M8.4.13), 64 columns,
   16 classes, 20 calls of the method's own `parse` and `run` with its memo filled, alternating two interval sizes; every call is checked to return the first call's columns.

## Results

| | Median | p95 (nearest rank) | Maximum |
|---|---|---|---|
| (1) One-tile edit, engine on, 18 samples | **71.9 ms** (JavaScript: 2.9 ms) | **793.8 ms** | 793.8 ms |
| (2) Remembered counts -> table of 349,526 rows (17,476 intervals) | **237.7 ms** | 671.1 ms | |

For (1): 17 of 18 samples lie between 70 and 117 ms; one sample, the first edit of the fifth pair, took 794 ms (it is the maximum and therefore the p95 of 18 samples; the
tool does not discard it). Whole-process memory and parity pass on the stand-in (418 MiB off, 536 on, limit 674; 0 mismatches). The interval change of all eight sections took 270 ms (median).

## Rule D11 (contract §7), as written

The engine computes the interval table of tiled sections (A) if p95(1) + median(2) <= 100 ms. Measured: 793.8 + 237.7 = 1,031 ms, and even the median of (1) plus the
median of (2) is 310 ms. **The rule's outcome is D**: the interval table and percentages of the interactive path would stay in JavaScript, with the Python method as reference.

## What the measurement also shows (for the design session; nothing was changed)

- **The 238 ms of (2) is an implementation artefact, not a property of the design.** A profile shows 225 of the 310 ms in `kernels/binning.py::sum_by_interval`, a Python loop
  with one NumPy call per interval (127,565 calls for 17,476 intervals x 7 sums). The sums are integer sums over row counts, exactly computable in one pass with cumulative sums.
  With that loop vectorised (a change of a kernel, which needs the usual reference fixtures and exact-equality tests and was outside this card), (2) would be a few milliseconds.
  The outcome of the rule would then depend on (1).
- **(1) is 70-117 ms in 17 of 18 samples**: the fixed cost of the chain (about 33 ms of bridge calls, 15-20 ms in the engine, the page's full hash of the masks and 30-50 ms of
  redraw, see M8.4.5) is already near the 100 ms of the rule for a section of one tile. The 794 ms sample is a stall (first edit after a warm-up; the engine's worker is restarted
  after any anomaly and was not asked to log one); with six pairs it cannot be told whether it recurs.
- **The 100 ms threshold is stricter than the 150 ms target** of contract §7 on purpose; the interval-table target of the tiled path would be met by (1) at its median.

## Decision recorded

ARCHITECTURE D11: outcome **D by the rule as measured (15 November 2026)**; a design session must decide, before card M8.4.14, between (i) accepting D, (ii) vectorising
`sum_by_interval` as its own card and repeating this measurement, or (iii) a different rule. Until then the interval table of tiled sections is **not** assumed to be in the engine.

Not measured: macOS and Linux (not part of the rule), a clean machine, saturated CPU, more than six pairs.
