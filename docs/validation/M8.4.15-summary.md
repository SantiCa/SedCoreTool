# M8.4.15 - The viewer of tiled sections against contract §7 (Windows, development evidence)

Raw data: [rgb2g](M8.4.15-viewer-rgb2g-windows.json), [gray16_2g](M8.4.15-viewer-gray16_2g-windows.json), [rgb8g](M8.4.15-viewer-rgb8g-windows.json),
[deflate8g](M8.4.15-viewer-deflate8g-windows.json), [small section tiled and not](M8.4.15-small-windows.json). Tool: `tools/measure_tiled_viewer.mjs`
(the real desktop program with the engine experiment and `SEDCORETOOL_TILED_SECTIONS=1`; window 1440 x 900; a fresh program per run, so the
pyramid comes from the cache of the previous run). Computer: Windows 11, AMD Ryzen 7 7700X (16 logical CPUs), 31 GiB. Fixtures of
[M8.4.13](M8.4.13-large-baseline-summary.md). Disk cache warm (cold-disk numbers are not claimed). One measured run per file, except `gray16_2g` (three).

## Result against the targets of the card

| Target | rgb2g (2 GiB) | gray16_2g (2 GiB) | rgb8g (8 GiB) | deflate8g (7.4 GiB file) |
|---|---|---|---|---|
| First useful view <= 2 s (click on "Add here" to the first frame, pyramid cached) | **2,156 ms - missed** | **2,031 / 2,072 / 2,140 ms - missed** | **6,675 ms - missed** | **6,503 ms - missed** |
| Cached pan and zoom, frame median <= 17 ms | 6.8 ms | 6.7 ms | 6.7 ms | 7.1 ms |
| Cached pan and zoom, frame p95 <= 33 ms | 8.8 ms | 9.8 ms | 11.0 ms | 10.8 ms |
| Uncached jump: first frame shows image (never blank) | yes (20 of 20) | yes | yes | yes |
| Uncached jump: full resolution within 250 ms p95 | 182 ms | 336 ms first run; **89 and 78 ms** in two repeats | 187 ms | 207 ms |
| Process-tree peak <= 2 GiB | 1,292 MiB | 1,397 / 1,375 / 1,338 MiB | 1,548 MiB | 1,468 MiB |

Notes on how each number was taken. *Frame cost* is the time from the start of the animation frame to the end of the page's render (120 frames of a scripted
pan of +-150 source pixels and a zoom between 1 : 1 and 2.5 : 1 over tiles already loaded); the frame interval was 8.3 ms (a 120 Hz display), so the cost, not
the interval, is the quantity. *Uncached jump*: 20 jumps to random rows at 1 : 1; the time is until the scheduler has nothing left to fetch, which includes the
ring of one tile around the visible ones, so it overstates the time of the visible tiles; with 20 samples the p95 is the maximum. The first run of
`gray16_2g` came right after the pyramids of the other files had been read (cold parts of the disk cache); the repeats did not. *Memory* is the sum of the
working sets of the whole process tree (Electron and the engine), sampled every 250 ms, which counts shared pages more than once, so it is an upper bound.

## Why the first view is slow

Not the viewer: with the pyramid already on disk, `pyramid.build` still takes 1.85 s for the 2 GiB file (measured inside the page, 1,864 ms of the 1,927 ms
before the section is selected). The pyramid is identified by the SHA-256 of the whole source file (contract §8), and the engine reads and hashes the source
every time it is added, before it can see that the pyramid exists. SHA-256 of a file runs at about 1.1 GB/s here, so 8 GiB costs about 7 s - the 6.5 s measured.
The registration, the reading of the working level (11 tiles for `rgb2g`, 44 ms) and the first frame together take about 0.1 s.

## Small section tiled and not tiled (evidence for rule 6 of the card)

The public example (620 x 16,726, factor 2, working image 310 x 8,363), the same scripted pan and zoom in working-image coordinates (2 to 5 screen pixels per
working pixel, so the tiles are drawn in the tiled run):

| | Not tiled (today's path) | Tiled (flag on) |
|---|---|---|
| Frame cost, median / p95 | 6.1 / 8.8 ms | 6.2 / 8.1 ms |
| First useful view (pyramid built in the same step) | 329 ms | 1,086 ms |
| Process-tree peak | 810 MiB | 743 MiB |

Panning and zooming cost the same; what a tiled section adds is the build of the pyramid on the first import.

## Decision needed (the card stops here)

The first useful view misses its target on all four files: 2.0-2.2 s on the 2 GiB files, 6.5-6.7 s on the 8 GiB ones. The rest passes. The cause is not the
viewer but the identity of the pyramid. Options, none implemented:

1. **Remember the identity of a file already hashed.** Keep, next to the pyramids, a small record `(absolute path, size, modification time) -> SHA-256` written
   after a full hash; on a match with the same three values, use the recorded SHA-256 and skip hashing. A file that changed without changing its size and its
   modification time (to the nanosecond) would show the old pixels; mitigation: also hash the first, middle and last MiB. Changes the contract §8.1 (a new
   file in the pyramid folder; the pyramid format itself and the hash of the tiles are unchanged). First view then: about 0.1-0.2 s for any size.
2. **Accept and document.** The wait happens only when an already-built file is added again (2-7 s, with the progress dialog), never while viewing; change the
   target to "first useful view <= 2 s for a file whose pyramid is identified quickly".
3. **Hash while showing progress** (no change of identity): the dialog already exists; the time stays 2-7 s.

Recommendation: option 1, with the sampled-MiB check. It touches the contract and the store, so it needs the maintainer's decision (card model: most capable tier).
