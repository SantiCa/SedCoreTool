# M8.4.15 - The viewer of tiled sections against contract §7 (Windows, development evidence)

Raw data: [rgb2g](M8.4.15-viewer-rgb2g-windows.json), [gray16_2g](M8.4.15-viewer-gray16_2g-windows.json), [rgb8g](M8.4.15-viewer-rgb8g-windows.json),
[deflate8g](M8.4.15-viewer-deflate8g-windows.json), [small section tiled and not](M8.4.15-small-windows.json). Tool: `tools/measure_tiled_viewer.mjs`
(the real desktop program with the engine experiment and `SEDCORETOOL_TILED_SECTIONS=1`; window 1440 x 900; a fresh program per run, so the
pyramid comes from the cache of the previous run). Computer: Windows 11, AMD Ryzen 7 7700X (16 logical CPUs), 31 GiB. Fixtures of
[M8.4.13](M8.4.13-large-baseline-summary.md). Disk cache warm (cold-disk numbers are not claimed). One measured run per file, with the identity record of the decision below (17 November 2026, evening).

## Result against the targets of the card (final code)

Every target is met.


| Target | rgb2g (2 GiB) | gray16_2g (2 GiB) | rgb8g (8 GiB) | deflate8g (7.4 GiB file) |
|---|---|---|---|---|
| First useful view <= 2 s (click on "Add here" to the first frame, pyramid cached) | 809 ms | 823 ms | 912 ms | 920 ms |
| Cached pan and zoom, frame median <= 17 ms | 6.3 ms | 5.9 ms | 5.9 ms | 5.8 ms |
| Cached pan and zoom, frame p95 <= 33 ms | 8.4 ms | 8.1 ms | 8 ms | 7.9 ms |
| Uncached jump: first frame shows image (never blank) | yes (20 of 20) | yes (20 of 20) | yes (20 of 20) | yes (20 of 20) |
| Uncached jump: full resolution within 250 ms p95 | 185.8 ms | 75.9 ms | 193.2 ms | 121.5 ms |
| Process-tree peak <= 2 GiB | 1,297 MiB | 1,324 MiB | 1,594 MiB | 1,551 MiB |

Notes on how each number was taken. *Frame cost* is the time from the start of the animation frame to the end of the page's render (120 frames of a scripted
pan of +-150 source pixels and a zoom between 1 : 1 and 2.5 : 1 over tiles already loaded); the frame interval was 8.3 ms (a 120 Hz display), so the cost, not
the interval, is the quantity. *Uncached jump*: 20 jumps to random rows at 1 : 1; the time is until the scheduler has nothing left to fetch, which includes the
ring of one tile around the visible ones, so it overstates the time of the visible tiles; with 20 samples the p95 is the maximum. The first run of
`gray16_2g` came right after the pyramids of the other files had been read (cold parts of the disk cache); the repeats did not. *Memory* is the sum of the
working sets of the whole process tree (Electron and the engine), sampled every 250 ms, which counts shared pages more than once, so it is an upper bound.

## The first view before the decision, and why it was slow

The first measurement (same day, before the identity record) missed the first-view target on every file: 2,156 ms (`rgb2g`), 2,031 / 2,072 / 2,140 ms
(`gray16_2g`, three runs), 6,675 ms (`rgb8g`), 6,503 ms (`deflate8g`); the other targets passed, with one uncached-jump p95 of 336 ms on `gray16_2g` taken
right after the other pyramids had been read (89 and 78 ms in two repeats). The cause was not the viewer: with the pyramid already on disk, `pyramid.build`
still took 1.85 s for the 2 GiB file (1,864 ms of the 1,927 ms before the section was selected, measured inside the page), because the pyramid is identified
by the SHA-256 of the whole source file and the engine read and hashed it every time it was added (about 1.1 GB/s here, so about 7 s for 8 GiB).

## Small section tiled and not tiled (evidence for rule 6 of the card)

The public example (620 x 16,726, factor 2, working image 310 x 8,363), the same scripted pan and zoom in working-image coordinates (2 to 5 screen pixels per
working pixel, so the tiles are drawn in the tiled run):

| | Not tiled (today's path) | Tiled (flag on) |
|---|---|---|
| Frame cost, median / p95 | 6.1 / 8.8 ms | 6.2 / 8.1 ms |
| First useful view (pyramid built in the same step) | 329 ms | 1,086 ms |
| Process-tree peak | 810 MiB | 743 MiB |

Panning and zooming cost the same; what a tiled section adds is the build of the pyramid on the first import.

## Decision and result

The maintainer chose option 1 of three (17 November 2026): remember the identity of a file already hashed. The other options were to accept and document the
wait (2-7 s, only when an already-built file is added again) or to hash with progress shown (same wait). Implemented in `src/sedcoretool/store/identity.py`
(contract §8.2 and §8.4): after a full hash the engine records the absolute path, size, modification time (ns), the SHA-256 of the first, middle and last MiB
and the full SHA-256 in `<root>/identities.json`; when all of them match again, the existing pyramid is used without reading the file whole. The record is
never used to build. Known limit: a file rewritten in place with the same size, the same modification time to the nanosecond and the same sampled MiB, but
other bytes elsewhere, is taken for its old state (`tests/test_store_identity.py` documents it). First view now 0.81-0.92 s on all four files. What remains
in it is mostly the list of the pyramid's files for `disk_bytes` (92-246 ms) and the start of the job; not broken down further.
