# M8.3.8 - Acceptance measurements of the first engine slice (Windows, development gate)

Raw data: [M8.3.8-engine-analysis-windows-v0.150.json](M8.3.8-engine-analysis-windows-v0.150.json), written by
`node tools/measure_engine_analysis.mjs` (commit, host and every sample are in the file). The slice is the method
`section.intervals/1` called from the desktop program with `SEDCORETOOL_ENGINE_EXPERIMENT=1`, run from source with the bundled
Python 3.12.16 runtime. Host: Windows 11 (10.0.26300), AMD Ryzen 7 7700X (16 logical CPUs), 31 GiB, Electron 45.2.2, Node 22.
This is **development evidence on one computer**: it is not a release-gate result.

Fixtures: the public six-section U1385I-1H example and the generated eight-section 960 x 6400 project of M0.1
(`tools/benchmark.py::make_synthetic`, PCG64 seed 138501), at 2 cm and 1.37 cm.

## Found while measuring

- A section whose inputs changed while its job waited was dropped without a new request and stayed *pending* (6 sections in 5 of 10
  cycles). Fixed in `app/js/engineanalysis.js` (a stale job asks again, `analyzeSections` waits for the newest revision) with two tests.
- A first measurement run compared "cold" analyses that the engine had already computed during project load; the tool now gives every
  cold analysis a new mask version.

## Corrections and second measurement (14 November 2026)

The first measurement failed one gate and showed the engine to be 60-160 times slower than JavaScript. Three corrections were made
and the whole measurement was repeated: [M8.3.8-engine-analysis-windows-corrected.json](M8.3.8-engine-analysis-windows-corrected.json)
(same tool, same fixtures, same computer; recorded commit `0f5978b` plus the uncommitted corrections, which are the next commit).

1. **One long-lived method worker** instead of one process per analysis (contract amended, see the "Job execution" paragraph of the
   contract). Starting the interpreter and NumPy took about 0.7 s of the 0.9 s a large section needed.
2. **Memory sampler** `tools/process_tree_sampler.py` (`psutil`, the Electron process and all its descendants): median gap 25.4 ms
   (contract: 25 ms), one gap of up to 155 ms in a run of 106 samples. Before it was 900 ms. The process counts of the two samplers
   are not comparable (the old one matched executable paths, the new one counts every descendant of Electron: 8 idle).
3. A bug of the new worker found by its own tests: an answer the coordinator does not approve left the job waiting forever. Fixed.

What this does and does not show:

- The engine is still 30-60 times slower than JavaScript on cold analysis. The time that remains per section is the snapshot and the
  upload of the label image (about 250 ms for 6 Mpixel) plus the NumPy calculation (about 100 ms against 20 ms in JavaScript). The
  upload disappears only when the engine owns the images (milestone M8.4); the calculation is not optimised yet.
- The memory gate passed in four of four runs with the 25 ms sampler. The first measurement's +109.7 MiB came from a sampler that took one sample
  per 0.9 s of a tree whose memory moves in steps of 100 MiB or more (Electron's renderer and GPU processes); it does not show that the
  engine was or was not the cause. Run-to-run spread of the final minus first value is about 60 MiB, so the margin to the gate is not large.
- A coordinator that dies still leaves the engine unavailable until the program is restarted (visible, no fallback). A restart on demand
  needs a decision about how the interface retries; it is left open.
- Still development evidence on one Windows computer; the "Not measured" list above is unchanged.

## Not measured

macOS and Linux; a clean Windows machine; cold cache after a reboot; saturated CPU; package sizes; the 25 ms memory cadence; the
packaged (installed or ZIP) program, which was run from source here. These stay on the release checklist.

## For the maintainer's decision

After the corrections every measured gate passes on this computer. The slice remains slower than JavaScript (30-60 times on cold
analysis) for a reason M8.4 removes: the page uploads each label image to the engine. Recommendation: continue to M8.4 and make the
engine own the images; the experiment stays off by default and the release-gate list is unchanged.
