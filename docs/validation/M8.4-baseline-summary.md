# M8.4.1 - Baseline of the warm scenarios (Windows, development evidence)

Raw data: [M8.4-baseline-windows.json](M8.4-baseline-windows.json), written by
`node tools/measure_engine_analysis.mjs --only scenarios --pairs 6 --synthetic <package>`; rules of the verdicts in
`tools/engine_gates.mjs` (tested), scenarios defined in [contract §7](../roadmap-engine-contract.md#7-predeclared-verification-and-performance-gates).
Same computer as M8.3.8 (Windows 11, Ryzen 7 7700X, 31 GiB, Electron 45.2.2, bundled Python 3.12.16), run from source, commit recorded in the
file. One unrecorded warm-up pair, then six alternating AB/BA pairs of fresh processes; the p95 of so few samples is the maximum.
Public example: six sections. Synthetic: the eight-section 960 x 6400 project of M0.1. **Baseline before any M8.4 optimisation.**

Milliseconds, median of the pooled samples (flag off = JavaScript, on = engine), and the limit of §7 for the median:

| Scenario | Public off | Public on | Limit | Synthetic off | Synthetic on | Limit | Verdict |
|---|---|---|---|---|---|---|---|
| (a) interval size changes, all sections | 1.4 | 1,778.6 | 51.4 | 1.3 | 3,730.1 | 51.3 | **fail** |
| (b) edit, undo, redo of one trace | 9.3 | 358.2 | 59.3 | 18.4 | 569.2 | 68.4 | **fail** |
| (c) unchanged re-analysis | 1.1 | 0.2 | 51.1 | 1.2 | 0.2 | 51.2 | pass |

The p95 limits fail in (a) and (b) as well (public (b): engine 1,835 ms against a limit of 785 ms; the JavaScript p95 there is 523 ms
because one of its edit samples was slow, so that limit is looser than the others).

Other gates measured in the same runs: **whole-process memory peak passes** (public 796 MiB off, 880 MiB on, limit 1,052; synthetic 836 / 1,010,
limit 1,092; the sampler now runs in both modes); **parity passes** (0 mismatches against the JavaScript reference after the interval change, the edit,
the undo and the redo, every section `ready`, the deleted trace restored by undo and removed again by redo).

What it says: scenario (c) already passes because the engine path caches by revision. (a) and (b) fail by a factor of 35 to 3,000 because every new
revision uploads the 25-30 MB of masks and recomputes everything in the engine, while JavaScript changes the interval size from its cached row counts
in about 1 ms. Cards M8.4.2 (resident inputs), M8.4.3 (reused row counts, one result buffer) and M8.4.4 (changed rows only) target exactly these two
scenarios. Not measured here: macOS, Linux, a clean machine, cold cache, saturated CPU. The edit is the deletion of a trace (the interface's Delete
key), not a paint stroke; its cost in JavaScript includes the recount of the section.
