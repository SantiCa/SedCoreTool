# M8.4.13 - what the current program does with multi-gigabyte images

Raw data: [M8.4.13-large-baseline-windows.json](M8.4.13-large-baseline-windows.json) (`tools/measure_large_images.mjs`, one fresh desktop
program per file and mode). Files: `tools/make_large_fixtures.py` (seed 138501, 8,192 pixels wide, written outside the repository; the six
TIFF files were checked on 20 regions each against the generator's function with the program's own reader). Computer: Windows 11 (10.0.26300),
AMD Ryzen 7 7700X (16 logical CPUs), 31.1 GiB RAM, Node 22.23.4, Electron 45.2.2; the engine experiment off and on. One run per case.

## What happened

Every file was **added**, with the engine off and on. Nothing was refused and nothing failed. The program does not load the full image: it
decodes the TIFF in blocks and keeps a working image of at most 8 megapixels (the default limit), reduced by the factor shown.

| File | Decoded | Factor | To first frame, off / on | Peak memory (process tree), off / on | Interval table, off / on |
|---|---|---|---|---|---|
| rgb2g (tiled) | 2 GiB | 10 | 7.9 / 6.7 s | 1,426 / 1,501 MiB | 24 / 123 ms |
| strip2g (striped) | 2 GiB | 10 | 9.2 / 6.7 s | 1,323 / 1,539 MiB | 15 / 125 ms |
| gray16_2g (16-bit) | 2 GiB | 12 | 8.6 / 7.5 s | 1,412 / 1,657 MiB | 25 / 146 ms |
| rgb4g | 4 GiB | 14 | 15.5 / 12.9 s | 1,581 / 1,714 MiB | 26 / 125 ms |
| rgb8g | 8 GiB | 19 | 29.1 / 24.9 s | 1,693 / 1,806 MiB | 27 / 130 ms |
| deflate8g | 8 GiB (7.4 GiB file) | 19 | 60.9 / 54.9 s | 1,120 / 1,174 MiB | 39 / 136 ms |
| jpeg (4,096 x 65,500) | 0.8 GiB | 6 | 2.6 / 4.5 s | 2,564 / 2,810 MiB | 16 / 133 ms |

With the working resolution set to "original", `rgb2g` was **not attempted**: its decoded RGBA raster would be 2.7 GiB, above the 2 GiB that
one typed array can address in this program. The same limit applies to every TIFF here (all decode to 2 GiB or more as RGB, so more as RGBA). The
JPEG (1.0 GiB as RGBA) would fit but the original-resolution run was requested only for `rgb2g`, so it is **not measured**. In effect no image
was shown at its full resolution.

## Interaction on the reduced working image

Pan for 3 s, ten zoom steps, 60-event brush stroke: the p95 frame gap was 4.2-8.3 ms and the p95 input-to-next-frame 2.6-6.1 ms in every case,
engine off and on. These numbers describe a **reduced 8-megapixel image in a headless program**, so they say that the existing display path is
fluid at that size, and nothing about fluidity at full resolution, which no case reached. The interactive targets of contract §7 are not
claimed by this card.

## What this shows

1. The limit today is not a failure but **detail**: a 349,526-row core is shown at 1/19 of its resolution. Reaching full resolution is what
   part C (tile store) adds; the whole-image path cannot do it because of the 2 GiB typed-array limit.
2. The cost is paid at import: the program reads the whole file once, 8-61 s here (the compressed 8 GiB file is the slowest). Memory stays
   below 2.9 GiB for every file, far under the file sizes.
3. The interval table with the engine on is 120-146 ms against 15-39 ms in JavaScript (the known whole-image overhead of M8.3/M8.4, here on
   a reduced image).
4. The JPEG has the highest memory peak (2.6-2.8 GiB) although it is the smallest file: the browser's decoder holds the whole bitmap.

## Proposal for the design session (not a decision)

Tile a section when its pixel count exceeds the working budget (today 8 megapixels, the point where the factor first exceeds 1), because that is
exactly where the whole-image path starts discarding detail; keep the whole-image path below it. Evidence for a different threshold would need a
measurement the baseline did not make: images between 8 megapixels and the typed-array limit at full resolution (for example 0.25-0.5 GiB).

## Not measured

macOS, Linux, a computer with 16 GiB (listed as not measured), repeated runs (one run per case, so no spread), full-resolution display, cold
disk cache (the files had just been written and verified), a real display (the program ran headless, so the frame gaps of 4 ms may not match what a screen shows), the JPEG at original resolution.
